После перевода программы на статический список локальный desktop Lighthouse: 66/100, FCP 0,5 с, LCP 0,6 с, TBT 840 мс, SI 3,0 с. Длинная задача 842 мс теперь в `/_astro/Base.astro_astro_type_script_index_0_lang.CQbWle3x.js`; гидрация `CourseProgram` ушла.

### Почему mobile и desktop расходятся

TBT считает задачи между FCP и TTI. На мобильном сеть и CPU медленнее, `client:idle`-острова могут гидрироваться после TTI и не попадать в TBT. На десктопе тот же код успевает гидрироваться раньше и попадает в окно измерения. Поэтому TBT нельзя сравнивать между mobile и desktop напрямую. После статической программы остаток на десктопе - уже не гидрация программы, а инициализация `Base`.

### Подтверждённый лишний пересчёт

В опубликованном профиле обнаружено изменение класса `dark` из `ThemeToggle`, входящего в `NavBar`. После него браузер пересчитал стили 1635 элементов за 194 мс. `Base` при первом входе без сохранённого выбора применяет системную тему, а прежний `ThemeToggle` при подключении React всегда выбирал тёмную. На светлом устройстве происходила непрошеная смена оформления уже после появления текста.

Также проверены два связанных дефекта прежнего компонента:

- сохранённая светлая тема вызывала несовпадение серверной и клиентской иконок и ошибку гидратации `NavBar`;
- мобильная и компьютерная кнопки хранили независимые состояния, поэтому после переключения могли показывать разные иконки;
- `color-scheme` оставался прежним после смены темы, и нативные элементы управления могли не соответствовать оформлению страницы.

### Локальное исправление

- `ThemeToggle.tsx`: единый источник состояния - уже применённый класс корневого элемента; `useSyncExternalStore` обеспечивает одинаковый первый серверный/клиентский рендер и синхронизирует обе кнопки через событие `hutba:theme-change`.
- При подключении React тема страницы не переписывается и выбор в хранилище не создаётся автоматически. По нажатию одновременно обновляются класс, `data-theme`, `color-scheme`, сохранённый выбор и обе кнопки.
- `Base.astro`: недоступность `localStorage` не мешает применить системную тему до появления текста.

Проверено через существующий dev-сервер: первый вход со светлой и тёмной системной темой, сохранённые светлая и тёмная темы, нажатия мобильной и компьютерной кнопок, согласованность иконок и `color-scheme`, сохранение выбора после перезагрузки. В четырёх обычных сценариях ошибок страницы и гидратации нет. При полностью заблокированном хранилище обе кнопки темы работают; у страницы остаётся отдельная ошибка `Blocked` вне подтверждённой проверки темы, устойчивость всех функций сайта к запрету хранилища не проверялась.

Для первого входа со светлой темой наблюдатель до правки фиксировал поздний переход `light -> dark`, после правки изменений класса темы при подключении React нет. Проверено визуально на мобильном экране. Сборка не запускалась, коммит и публикация не выполнялись.

Это исправление убирает подтверждённый лишний пересчёт темы, но не объявляется решением всей задачи 1002 мс и не даёт нового значения PSI. После публикации нужно повторить тот же урок 40 с одинаковым выбранным оформлением и сопоставить длинные задачи, TBT и LCP. QCF, wasl, Mermaid и framer-motion оставлены в прежнем режиме.

### Уточнение владельца: тёмная тема по умолчанию

После описанного профилирования владелец уточнил требование: без сохранённого выбора сразу включать тёмную тему независимо от настроек устройства. В `Base.astro` это применяется скриптом в `head`, до первого отображения страницы; `ThemeToggle` при подключении React тему не меняет. Сохранённое значение `light` имеет приоритет. Такое же правило установлено на странице перенаправления учебника «6 столпов», включая фон до перенаправления. ## 24. Серверный HTML блоков Корана в теории, шархах и словаре

По просьбе владельца обработка переносится на сервер и при последующих переходах, а не только откладывается до первого материала с аятами. Правка пока локальная.

### Как работает

- src/lib/interactive/serverHtml.ts объединяет серверную подготовку теории и шарха: marked, замена тегов Корана, подготовка Mermaid. prepareInteractiveLesson использует тот же код для первого HTML страницы.
- GET /api/interactive-html возвращает готовый HTML материала. Для теории передаются subject, course и source; файл выбирается точным совпадением в серверном glob данного курса. Для шарха передаётся только номер бейта. Произвольный HTML от браузера не принимается, чтения произвольного пути с диска нет.
- Успешный ответ имеет Content-Type text/html, ETag и Cache-Control public, max-age=0, must-revalidate. Неизменившийся материал возвращает 304 без тела, поддерживаются слабые ETag после сжатия прокси. Пропущенные параметры дают 400, несуществующий материал 404.
- TheoryReveal запрашивает готовый HTML при открытии другой теории. Клиентский glob Markdown, marked и replaceQuranTags удалены. Начальный initialHtml сохраняется, поэтому первый урок не зависит от дополнительного API-запроса. Запрос отменяется при уходе, ошибка имеет кнопку повторной загрузки. RenderBlock передаёт контекст курса и использует ключ с предметом, курсом и источником.
- MatnBlock получает HTML шарха по номеру бейта. Повторное раскрытие использует уже полученный результат; параллельные запросы одного бейта объединяются. При уходе запросы отменяются; при ошибке доступна повторная попытка. После вставки HTML повторно инициализируются аудиокнопки и обработка диаграмм. Поиск нужного шарха через #term сохраняется.
- Для словаря добавлен серверный prepareGlossaryEntry. Исходная статья и её статический JSON содержат уже раскрытые теги Корана; React-компоненты вставляют готовый body без обработчика. В TSX-компонентах больше нет импортов обработчика или рендерера Корана. В проверенных браузерных переходах отсутствуют запросы к replaceQuranTags, quranRenderer, полным JSON Корана, marked и сырым theory Markdown. Обычные текстовые уроки и раньше готовили аяты на сервере, их обработка не менялась.
