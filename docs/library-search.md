# Основной план поиска библиотеки HUTBA

Статус: основной план развития поиска по Корану, хадисам и тафсирам. Актуализирован 9 ноября 2026 года по данным и коду проекта `D:\Yandex.Disk\AstroProject`. Раздел «Что уже есть» описывает текущую реализацию; остальные разделы определяют предлагаемые изменения. Архивный `QURAN-search-plan.md` сохраняется как история исследования источников.

## 1. Что предлагается

Подключить проверенный тематический указатель как дополнительный способ находить аяты в библиотеке. Пользователь должен находить материал и по словам оригинала или перевода, и по вопросу, который описан другими словами.

Например, при поиске вопроса о сохранении семьи система сможет предложить подходящую рубрику указателя и связанные аяты, даже когда формулировка запроса буквально не встречается в переводе. При этом рядом с каждым аятом можно показать уже сохранённое объяснение: почему он отнесён к этому вопросу и на каком основании.

Начать стоит с обычного поиска и проверенных связей. Векторный поиск и LLM подключать следующим этапом, если замеры качества покажут, что существующих рубрик, словарей и полнотекстового поиска недостаточно. Для первой версии не нужны платные API и автоматическая генерация новых толкований.

Базовая схема:

```text
Запрос пользователя
  -> распознавание адреса аята или номера хадиса
  -> параллельный поиск:
       текст Корана и перевод
       темы и конкретные описания указателя
       текст хадисов и их пояснения
       русский тафсир Саади
  -> объединение совпадений с сохранением их происхождения
  -> результаты с местными ссылками и пояснением причины попадания
  -> при необходимости: ответ LLM только по отобранным материалам
```

## 2. Что уже есть

### Библиотека и поиск

Страницы библиотеки:

- `/quran/read` - Коран, перевод и русский тафсир.
- `/hadith-sbornik/bukhari` - Сахих аль-Бухари.
- `/hadith-sbornik/muslim` - Сахих Муслима.
- `/hadith-sbornik/abudawud` - Сунан Абу Дауда.
- `/quran/index` - отдельный просмотр тематического указателя.

Адрес `/quran/` занят курсами, поэтому чтение Корана выделено в `/quran/read`. Старые адреса внутри `/hadith-sbornik/` не поддерживаются; перенаправлений нет.

Поиск уже работает через `src/pages/api/hadith-reader.json.ts`, действие `action=search`. Основные функции находятся в `src/lib/hadith/reader.ts`, `quranReader.ts`, `collections.ts` и `searchText.ts`.

Система нормализует запрос и ищет наличие всех его слов в текстах. Для Корана также распознаётся точный адрес вида `2:255` (допускаются пробелы вокруг двоеточия). У хадисов проверяются номера. Выдача разбита на страницы по 30 результатов.

9 ноября 2026 года добавлен первый этап тематического поиска. Модуль `src/lib/library-search/topics.ts` ищет по названиям, конкретным описаниям и отдельным пояснениям проверенного указателя. Название широкой темы не заменяет узкое описание: для запроса из нескольких слов проверяется соответствие описания либо конкретного пояснения. Для тем без собственных аятов используются только разрешённые перекрёстные ссылки из `audit.crossreference_resolution`, с защитой от циклов и ограничением глубины.

В API сохранены старые параметры и добавлен `group=all|topic|ayah|hadith`, счётчики групп и ограниченные страницы тем. В интерфейсе есть отдельная группа «Темы» и тематические причины попадания аятов. Аят выводится одной карточкой; показываются до трёх причин с основаниями, источниками, контекстом и оговорками, а остальные доступны через указатель. При чтении аята выводится небольшой список связанных описаний. Переход с параметром `item` открывает нужное описание в `/quran/index`.

Словарь `src/lib/library-search/synonyms.ts` применяется только к указателю: восемь групп вариантов имён и пять целых формулировок, ведущих к существующему описанию о примирении супругов. Это редакционные поисковые варианты, а не новые связи с аятами. Исходные корпуса не изменяются. Отрицание не удаляется; целая формулировка с отрицанием не активирует положительный поисковый вариант.

У текущего механизма есть ограничения:

- Тафсир Саади доступен при чтении, но не входит в поисковые строки Корана.
- Единого ранжирования корпусов пока нет. В общем поиске аяты располагаются перед хадисами; доступны отдельные группы. Внутри поиска Корана буквальные совпадения идут перед тематическими; тематические связи упорядочены по приоритету описаний.
- В поисковой строке хадиса объединены русский текст, арабские части и русские пояснения. Совпадение в пояснении может давать результат, хотя показанный фрагмент основного текста не содержит искомых слов.
- Наличие всех слов в большом тексте не гарантирует ответа на вопрос пользователя.
- Фильтр оценки применяется только к хадисам и сохраняет аяты и темы. Отдельные группы показывают число результатов после фильтрации хадисов.

### Данные указателя

В `src/data/quran-index/index.json` находятся:

- 539 тем;
- 2429 конкретных описаний внутри тем;
- 25711 связей описаний с аятами;

Это число связей, а не число независимых текстов Корана. Один аят может входить в несколько рубрик. В указателе есть также темы со ссылками на другие темы, без собственных аятов. Отсутствие аята в указателе не должно исключать его из обычного поиска Корана.

У каждой связи есть `explanation`, короткая цитата `key_phrase`, основание `basis` и `source_ids`. При наличии нужно сохранять `qualification`, `context_verse_keys` и `usage_note`. Эти поля помогают объяснить результат и не преувеличить значение найденной связи.

## 4. Как использовать темы и описания

Искать на двух уровнях:

1. **Тема:** название, имеющиеся варианты имени или названия, ссылки на другие темы.
2. **Конкретное описание:** `items[].description`, пояснения связей и ключевые цитаты.

Приоритет отдавать конкретному описанию. Совпадение с широкой темой вроде имени или общего понятия не означает, что все сотни связанных с этой темой аятов отвечают на узкий вопрос.

Для названий и имён полезен небольшой проверяемый словарь вариантов написания: например, формы имени пророка, варианты русской транслитерации и обычные поисковые формулировки. Хранить его отдельно от священного текста. Новые синонимы сначала проверять на ложные совпадения. Не расширять запрос механической подстановкой всех похожих по смыслу религиозных терминов.

Для темы без собственных аятов переходить по разрешённой перекрёстной ссылке. Учитывать циклы и ограничивать глубину обхода. Не показывать отсутствие собственных ссылок как доказательство отсутствия упоминания в Коране.

### Основание связи обязательно сохранять

| Основание | Как пояснять результат |
| --- | --- |
| Непосредственный текст | «Соответствие по тексту аята» |
| Контекст | «Соответствие с учётом соседних аятов» |
| Толкование | «Отнесено к теме в тафсире...» |
| Именное отнесение | «В таком толковании аят связывается с...» |
| Хадис | «Связь поясняется хадисом...» |
| Языковой разбор | «Соответствие основано на языковом разборе» |

Это предлагаемые понятные подписи. Точные внутренние значения брать из `basis_definitions` и существующих записей, не заменяя их произвольной новой классификацией.

Если есть оговорка или разногласие, показывать их рядом с пояснением. Особенно это важно для людей, не названных в самом аяте. Формулировка из тафсира не должна превращаться в утверждение «это имя прямо названо в Коране».

## 5. Обратные связи для чтения и поиска

Из существующих данных можно подготовить компактные таблицы соответствий:

- `verse_key -> topic_id + item_id` - какие темы связаны с открытым аятом.
- `topic_id -> item_id -> verse_keys` - выдача по выбранному описанию.
- `source_id -> topic_id + item_id + verse_key` - в каких конкретных пояснениях использован источник.
- `collection + record_id -> source_id` - какие местные хадисы уже связаны с пояснениями указателя.

Эти таблицы являются производными от проверенного файла. Они не создают новых смысловых связей и могут автоматически пересобираться после изменения исходника.

На странице аята можно добавить «Связанные темы»: несколько подходящих описаний с переходом в `/quran/index`. Поиск по теме и чтение аята тогда станут двумя входами к одним данным.

### Важное ограничение для хадисов

Указатель является тематическим индексом аятов. Он не размечает все хадисы трёх сборников по темам.

Без новой ручной проверки допустима только такая связь: конкретный хадис указан в `source_ids` конкретного пояснения к конкретному аяту. В интерфейсе её следует назвать «Хадис, использованный в пояснении к аяту».

Нельзя автоматически приписывать этому хадису все темы, к которым относится аят. Нельзя также считать весь сборник или все варианты похожего сообщения подтверждением конкретной связи.

Хадисы вне указателя продолжают участвовать в обычном поиске по тексту. Полноценный тематический указатель хадисов можно готовить отдельно и постепенно.

## 6. Как должна выглядеть выдача

В общей библиотеке оставить одну строку поиска, область поиска и понятные группы результатов:

- «Темы» - найденные рубрики и конкретные описания.
- «Аяты» - совпадения в тексте, переводе и проверенные тематические результаты.
- «Хадисы» - совпадения в местных сборниках.
- «Тафсир» - совпадения в русском толковании Саади.

Показывать количество результатов каждой группы. Одной группе не стоит занимать все первые страницы общего поиска. Для первой версии проще сделать отдельные вкладки с коротким обзором каждой группы, чем смешивать всё в единую непрозрачную оценку.

В карточке аята:

1. Адрес и местная ссылка на чтение.
2. Фрагмент текста или перевода.
3. Причина попадания: «Совпадение в переводе» либо название найденного описания указателя.
4. Короткое пояснение связи и основание, если результат тематический.
5. Возможность раскрыть контекст и источники.

Один аят показывать один раз в пределах группы, сохранив все подходящие описания внутри карточки. Совпадения в толковании не выдавать за буквальное совпадение в переводе аята.

В карточке хадиса показывать сборник, полный местный номер, фрагмент найденного поля, имеющуюся оценку и источник этой оценки. Если запрос найден только в пояснении, так и подписать: «Совпадение в пояснении», и показать фрагмент пояснения.

Фильтры: тип материала, сборник, язык текста, способ поиска. Оценка хадиса применяется только к хадисам. Отсутствие оценки не означает «слабый». Принадлежность к сборнику и оценка конкретной записи остаются разными признаками.

### Местные ссылки

- Аят: `/quran/read/ayah/2-255`. Этот маршрут открывает соответствующую суру и выбирает аят.
- Тема: `/quran/index?topic=<topic_id>`.
- Толкование из указателя: `/quran/index?tafsir=<source_id>#selected-tafsir`.
- Хадис: получать URL через существующий `recordPath` из `src/lib/hadith/collections.ts` или из проверенного соответствия `hadith-sources.json`.

Не собирать URL хадиса вручную только из числовой части номера: встречаются буквенные окончания и несколько местных записей с одним номером. Для идентичности использовать сборник и `record.id`.

Статус `pending_collection` у ат-Тирмизи и Ибн Маджи является заглушкой. Такую запись нельзя показывать как доступный полный хадис, включать в текстовый корпус или подменять внешним переходом.

## 7. Обычный поиск до RAG

### Нормализация

Текущая функция `normalizeSearch` уже убирает ряд огласовок, татвиль и поисковые различия арабских букв, приводит регистр и `ё` к `е`. Использовать её как общую отправную точку, проверяя изменения на русских и арабских запросах.

Нормализованная строка существует только для поиска. Отображать исходные символы и огласовки. Не менять оригинальный Коран ради удобства поиска. Подсветка найденного должна сохранять привязку к исходным позициям символов, как уже предусмотрено в `searchRanges`.

Для русского языка полезны формы слов и проверенные варианты названий. Для арабского сначала достаточно существующей нормализации и поиска слов и фраз. Корневой поиск требует отдельной проверки: одинаковый корень не равен одинаковому смыслу.

Арабский запрос не становится русским тематическим запросом автоматически. На первом этапе он ищет по арабским текстам и явно добавленным арабским названиям тем. Межъязычный смысловой поиск является отдельной возможностью следующего этапа.

### Поля хранить раздельно

У аята: адрес, арабский текст, перевод, название суры и ссылки на темы.

У описания указателя: название темы, описание, варианты написания, пояснения и ключевые цитаты. Оговорки учитывать при показе и оценке, а не использовать как слепой положительный сигнал совпадения.

У хадиса: арабские части, русский основной текст, пояснения, номера, книга, глава и данные оценки. Матн и иснад разделять там, где исходная структура позволяет сделать это достоверно. Не определять границы произвольным разрезанием предложений.

У тафсира: автор, язык, текст и адрес аята или подтверждённый диапазон. Не смешивать тафсир с переводом в одном безымянном поле.

### Ранжирование

Практический порядок приоритетов:

1. Точный проверенный адрес аята; для номера хадиса - совпадения с учётом выбранного сборника.
2. Точное совпадение названия темы, имени или фразы.
3. Совпадение с конкретным описанием указателя.
4. Совпадение слов и фраз в основном тексте и переводе.
5. Совпадение в пояснениях и тафсире с соответствующей подписью.
6. Более широкое тематическое или смысловое сходство.

Это ориентир, а не готовая универсальная формула. Весовые коэффициенты выбирать по контрольным запросам. Для длинного вопроса не требовать буквального наличия всех служебных слов; для точной цитаты предложить режим фразы. Вопросы с отрицанием, сравнением и условиями проверять отдельно.

Для начала можно подготовить обратные таблицы и поисковые строки на сервере. Если линейный перебор станет медленным, перейти к отдельному полнотекстовому индексу с оценкой релевантности, например SQLite FTS5 при наличии поддержки в используемом окружении. Конкретный движок выбрать после замера времени запросов, памяти и удобства обновления. Само наличие SQLite с тафсирами не означает, что поисковая база уже готова.

## 8. Предлагаемая техническая организация

Сохранить исходные корпуса и проверенный указатель отдельно. Дополнительные таблицы создавать как восстанавливаемые поисковые данные, без ручного редактирования копий священного текста.

Возможное размещение, пока только предложение:

```text
src/lib/library-search/
  query.ts            разбор запроса и адресов
  topics.ts           поиск по темам и описаниям
  ranking.ts          объединение и ранжирование
  links.ts            местные переходы
  types.ts            общий формат результата

var/library-search/
  manifest.json       версии исходников и настройки подготовки
  search.sqlite       производный полнотекстовый индекс, если он понадобится
```

Папка `var` и перечисленные модули этим документом не создаются. При выборе другого формата физическое размещение можно изменить. Важно, чтобы подготовка поисковых данных выполнялась отдельной командой и не требовала полной сборки сайта.

Существующий API можно расширить совместимо: сохранить старые параметры `q`, `scope`, `page`, `grade`, добавить явный режим и необходимые поля ответа. Либо выделить новый маршрут, сохранив старый для текущего интерфейса.

Полезные поля результата:

| Поле | Для чего |
| --- | --- |
| `kind` | Аят, хадис, тема или тафсир |
| `id`, `collection` | Устойчивая идентичность документа |
| `href` | Местный переход |
| `matched_field`, `match_type` | Где найдено и буквальный ли это результат |
| `snippet`, `language` | Фрагмент именно найденного поля |
| `verse_key` | Адрес аята, если применимо |
| `topic_id`, `item_id` | Конкретная тематическая связь |
| `basis`, `qualification`, `source_ids` | Проверяемое основание и ограничения связи |
| `grade`, `grade_source` | Имеющиеся сведения об оценке хадиса |
| `score` | Служебная оценка для сортировки, не процент достоверности |

Не передавать клиенту весь `index.json`, все сборники и все толкования ради одного запроса. На клиент отправлять только страницу результатов и раскрываемые сведения. Серверные производные данные можно переиспользовать между запросами; способ кэширования выбрать с учётом режима развёртывания.

## 9. Как затем подключать RAG и LLM

RAG здесь нужен для поиска материалов по свободному вопросу и составления ответа с проверяемыми ссылками. Он не должен менять текст аятов, создавать новые подтверждённые связи или заменять указатель.

### Что индексировать в векторной базе

- **Описание указателя:** тема, конкретное описание и проверенные пояснения. Это небольшой и полезный первый корпус для проверки смыслового поиска.
- **Аят:** исходный текст и перевод с адресом. Контекст добавлять при получении материалов, сохраняя отдельные адреса соседних аятов.
- **Тафсир:** фрагмент с автором и подтверждённой привязкой. Для длинного комментария сохранять связь частей с общим документом.
- **Хадис:** целая запись или обоснованно выделенный матн; длинные записи делить с сохранением `record_id`. Русские пояснения хранить как пояснения, а не как слова Пророка.

Арабский и русский текст можно индексировать отдельными представлениями одного документа, сохраняя общую идентичность. Выбор модели для двух языков проверять на реальных запросах. Не заявлять поддержку межъязычного поиска только потому, что база приняла оба текста.

Обязательные метаданные: тип корпуса, местный идентификатор, язык, редакция, SHA256 исходного файла, версия подготовки, адрес аята или номер и ID хадиса, автор перевода или толкования. Для фрагмента указателя также `topic_id`, `item_id`, `basis`, `source_ids` и оговорки.

Существующую коллекцию `hutba_knowledge`, где ранее готовились чанки уроков и эмбеддинги, пока не менять. Её аудит отложен владельцем. Для эксперимента выбрать отдельную версию или коллекцию; не считать старые уроки автоматически совместимыми с новой схемой.

### Получение материалов и ответ

1. Распознать точные ссылки и ограничения запроса.
2. Найти кандидатов обычным поиском, по темам и при необходимости по векторам.
3. Объединить кандидатов, убрать повторы, восстановить контекст и источники.
4. Передать LLM только отобранные материалы и их идентификаторы.
5. Проверить, что ссылки ответа действительно относятся к переданным документам.
6. Подставить цитаты оригинала и перевода из местных файлов, не доверяя воспроизведению модели по памяти.

Ответ должен различать: текст аята, перевод, толкование, сообщение хадиса и вывод составителя. Ограничения именных отнесений, разногласия и оценки хадисов нельзя терять при сокращении.

Если основания недостаточны, сообщить об этом и показать найденные материалы. Не превращать похожий фрагмент в уверенный религиозный вывод. Инструкции, случайно встретившиеся в текстах источников, рассматривать как содержимое документа, а не команды для LLM.

Источники ответа должны открываться в местной библиотеке. Адрес внешнего происхождения можно сохранять как библиографические данные; он не нужен для получения текста во время пользовательского запроса.

## 10. Очерёдность внедрения

### Этап 1. Темы без LLM

- Подключить поиск по названиям и конкретным описаниям указателя.
- Добавить отдельную группу «Темы» и тематические причины попадания аятов.
- Подготовить обратную таблицу аятов и добавить связанные темы при чтении.
- Обработать перекрёстные ссылки и сохранить оговорки.

Результат: тематический поиск уже полезен и проверяем, даже без эмбеддингов.

### Этап 2. Единая качественная выдача

- Разделить поля основного текста и пояснений.
- Подключить поиск по русскому Саади.
- Добавить ранжирование, подсветку нужного поля и фильтры с явной областью действия.
- Показывать местные хадисы, уже использованные в конкретных пояснениях указателя.

Результат: поиск не зависит только от буквального совпадения и не смешивает разные виды источников.

### Этап 3. Смысловой поиск

- Подготовить небольшой контрольный набор вопросов.
- Проверить эмбеддинги сначала на описаниях указателя.
- Сравнить результат с этапами 1 и 2, затем при подтверждённой пользе расширить корпуса.

Результат: можно обоснованно решить, где векторы помогают, а где добавляют ложные совпадения.

### Этап 4. Ответы с LLM

- Добавить отдельное действие «Составить ответ по найденному».
- Сохранять доступ к обычному поиску и полным документам.
- Проверять цитирование, ограничения источников и поведение при недостаточных данных.

Платные API, провайдер и расходы этим планом не согласованы. До их подключения нужно отдельно выбрать способ работы и стоимость.

## 11. Как проверить качество

Подготовить 50-100 запросов с ожидаемыми подходящими и заведомо неподходящими результатами. Набор сохранять отдельно от рабочих исходников. Примеры направлений:

| Проверка | Что должно получиться |
| --- | --- |
| `2:255` | Точный аят первым, без подмены тематической подборкой |
| Несуществующий адрес `13:94` | Нет результата с таким адресом |
| Русская форма слова и `ё/е` | Ожидаемые совпадения после поисковой нормализации |
| Арабская фраза с огласовками и без | Сопоставимая выдача, исходное начертание сохранено |
| Варианты написания имени | Нужная рубрика и сохранённые ограничения именного отнесения |
| «сохранение семьи» | Подходящие конкретные описания, без всех результатов широкой темы |
| Тема с перекрёстной ссылкой | Переход к действительной рубрике без цикла |
| Совпадение только в Саади | Подпись «Тафсир», а не «Текст аята» |
| Совпадение только в пояснении хадиса | Фрагмент пояснения и правильная подпись |
| Номер хадиса с буквенным окончанием | Номер не обрезан, правильная местная запись |
| Несколько вариантов одного номера | Правильные ссылки на варианты без случайного слияния |
| Фильтр оценки хадиса | Понятная область действия, отсутствие оценки не объявлено слабостью |
| Заглушка ат-Тирмизи или Ибн Маджи | Нет вымышленного текста и активной ссылки на отсутствующую запись |
| Один аят в нескольких описаниях | Одна карточка аята с несколькими причинами |
| Вопрос с отрицанием | Не выдаётся противоположное утверждение только из-за общих слов |

Измерять долю полезных результатов в первых 5 и 10 позициях, пропуски ожидаемых результатов, ошибочные тематические отнесения, правильность ссылок и цитат. Отдельно замерять холодный и повторный запрос, память сервера и размер ответа. Ориентир времени ответа установить после измерения на рабочем сервере, а не обещать заранее.

Для этапов с LLM дополнительно проверять каждое утверждение ответа по приведённому источнику. Автоматический контроль ссылок и совпадения цитат полезен, но не заменяет смысловую оценку.

Проверки выполнять через локальный сервер и точечные проверки данных. Полную сборку сайта не запускать без отдельной явной команды владельца.

## 12. Обновление и сопровождение

- В манифесте производного поиска хранить хеши исходников, версию схемы, нормализации и модели эмбеддингов, если она используется.
- Изменение текстового файла требует обновления его поискового представления; изменение привязок требует пересборки обратных таблиц.
- Перед публикацией проверить наличие всех адресов, ID записей и источников, отсутствие потерянных оговорок и дублирования карточек.
- Автоматическая пересборка не является новой смысловой проверкой. Новые связи и тематические расширения подтверждать отдельно.
- Готовить новую версию индекса отдельно и переключать её целиком, сохраняя возможность возврата. Не отдавать пользователям частично обновлённый набор.
- Не включать личные запросы пользователей в публичные отчёты; для оценки качества достаточно обезличенного контрольного набора.

## 13. Что сделать первым в следующей задаче

Первый этап подключён. Начальный набор из 50 запросов находится в `docs/library-search-queries.json`; команда `npm run test:library-search` проверяет функции, API-обработчик и серверный рендер React без запуска сборки. Набор фиксирует ожидаемые рубрики, описания, адреса, варианты имён, отрицания поисковых вариантов и номера хадисов с буквенными окончаниями. Проверяется сохранение полей найденных связей относительно исходного указателя. Эти проверки не заменяют смысловую оценку выдачи владельцем.

Следующий шаг: просмотреть первые 5 и 10 результатов контрольных запросов, добавить ожидаемые пропуски и ложные тематические совпадения. Затем выполнить этап 2: отдельные совпадения в Саади и пояснениях хадисов, соответствующие фрагменты и подписи. Решение о полнотекстовом движке и RAG принимать после замеров. Аудит `hutba_knowledge` остаётся отложенным.

Результаты проверки первой версии: 50 запросов и 92960 сверок проекций связей прошли. Контрольные HTTP-запросы к действующему локальному серверу подтвердили выдачу 4:35 и 4:128 для «сохранение семьи», сохранение 2:255 при фильтре хадисов и правильную запись Муслима 4a. Ответ для «сохранение семьи» составил 3542 байта; повторный замер HTTP занял 151 мс. Прямой переход к конкретному описанию и страница чтения аята также проверены по HTTP. Точечная строгая проверка типов нового модуля прошла без ошибок. Это локальные замеры, не норматив времени ответа и не измерение холодного старта. Визуальную проверку браузером выполнить не удалось из-за недоступности локального сервера из браузерного инструмента. Сборка не запускалась.

Сохраняется ограничение арабской нормализации: удаление надстрочного алифа в османском начертании не делает его эквивалентным обычному написанию с отдельным алифом. Контрольные примеры проверяют снятие огласовок на совпадающем буквенном составе; расширение орфографических соответствий требует отдельной проверки. Полной русской морфологии и смыслового разбора отрицаний в этой версии нет.
